Design Challenge — AI Latency

Hiding the wait
vs. showing the work.

Initial Approach — Rejected

Hide the process in the background

Processing...

Designed a flow where the AI pipeline ran silently in the background — users would see a minimal spinner while the depth map generated, with no visibility into what was happening or how long it would take.

✕
Caused user drop-off Frontier tech users expected instant results. With no feedback, they assumed the app was broken and abandoned during the loading phase. The wait time hadn't changed — but the experience felt like a failure.
pivot

Shipped Solution

Expose the AI work in real time

Image uploaded ✓
Generating depth map…
Stitching RGBD file
Depth Preview

Redesigned the loading state to visually expose each step of the AI pipeline — upload confirmed, depth generation live preview, stitching progress. Users could see the AI doing the work in real time.

✓
Eliminated drop-off during load By making the latency legible — and the depth map visually compelling — the wait became part of the experience. Users stayed engaged because they understood what was happening and it felt like magic.

Visual Craft — Hardware States

The device is
part of the UX.

Pushing spatial files over home Wi-Fi to v1 hardware introduced failure modes that purely digital products never encounter. Every state of the physical device had to be surfaced explicitly — in language a non-technical consumer could act on.

Design principle

A dropped Wi-Fi handshake is just as much a UX problem as a confusing button. If the user can't tell what the device is doing, they'll blame the app — or return the hardware.

Audience constraint: No engineering manuals. Every state label, icon, and progress indicator had to be self-explanatory for a consumer who had never owned spatial computing hardware before.

The key decision: Each state is explicit and actionable — not a generic spinner. Users always know what the device is doing, what to do next, and what not to do (e.g., don't unplug during firmware update).

Honest Retrospective

What designing for hardware taught me —

↑
Physical failure modes are UX problems A dropped Bluetooth handshake, a slow Wi-Fi transfer, a mid-update power cut — all of these are as much a design problem as a confusing button. Hardware adds an entirely new class of edge case.
↑
Latency on frontier tech requires honesty, not hiding The instinct was to hide the wait. The correct move was to make it legible and compelling. Transparency about AI processing built trust instead of eroding it.
→
I'd have pushed for more user testing on the hardware states earlier We got the device state language right — but largely through iteration after internal feedback. Earlier consumer testing would have accelerated it.
→
v1 hardware constraints shaped design decisions that may not age well Some UX choices were workarounds for hardware limitations that will be solved in v2. Worth documenting what's a design decision vs. a hardware constraint.
